INVOICEFLOW PLANO DE DESENVOLVIMENTO — ROADMAP / SPRINT PLAN

Stack: - React - JavaScript - Next.js com App Router - Tailwind CSS -
shadcn/ui - React Hook Form - Zod - Zustand - Supabase (Auth +
PostgreSQL + Storage quando necessário)

IMPORTANTE: este plano foi adaptado para JavaScript. TypeScript não faz
parte do projeto.

======================================================================
0. PRINCÍPIOS DE ARQUITETURA
======================================================================

1.  Separar UI, regras de negócio, acesso a dados e estado.
2.  Usar Server Components por padrão no Next.js e Client Components
    somente quando houver interatividade.
3.  Centralizar cálculos de orçamento em funções puras e testáveis.
4.  Usar Supabase como fonte persistente dos dados.
5.  Usar Zustand principalmente para estado temporário/interativo.
6.  Proteger dados privados com Row Level Security (RLS).
7.  Tratar orçamento enviado/aprovado como documento que não pode ser
    alterado silenciosamente.
8.  Construir primeiro o fluxo funcional completo e depois adicionar
    diferenciais.

2. MODELAGEM DE DADOS — SUPABASE / POSTGRESQL
======================================================================

REGRA ARQUITETURAL MAIS IMPORTANTE

O orçamento deve preservar os dados usados no momento em que foi criado.

Exemplo: - Hoje o serviço custa R$ 500. - Um orçamento é criado por R$
500. - Amanhã o serviço passa a custar R$ 800. - O orçamento antigo
continua mostrando R$ 500.

Por isso quote_items deve guardar um snapshot dos dados.

2.1 profiles

profiles

id UUID PK full_name TEXT email TEXT avatar_url TEXT NULL phone TEXT
NULL created_at TIMESTAMP updated_at TIMESTAMP

Relacionamento: auth.users 1:1 profiles

2.2 clients

clients

id UUID PK user_id UUID FK -> profiles.id name TEXT email TEXT NULL
phone TEXT NULL company TEXT NULL document TEXT NULL address TEXT NULL
notes TEXT NULL created_at TIMESTAMP updated_at TIMESTAMP

Relacionamento: profiles 1:N clients

2.3 services

services

id UUID PK user_id UUID FK -> profiles.id name TEXT description TEXT
NULL unit TEXT price NUMERIC created_at TIMESTAMP updated_at TIMESTAMP

Relacionamento: profiles 1:N services

2.4 quotes

quotes

id UUID PK user_id UUID FK -> profiles.id client_id UUID FK ->
clients.id

quote_number TEXT public_id UUID UNIQUE

title TEXT description TEXT NULL

status TEXT

subtotal NUMERIC discount_type TEXT discount_value NUMERIC
discount_total NUMERIC tax_total NUMERIC total NUMERIC

valid_until DATE NULL notes TEXT NULL terms TEXT NULL

created_at TIMESTAMP updated_at TIMESTAMP sent_at TIMESTAMP NULL
approved_at TIMESTAMP NULL declined_at TIMESTAMP NULL

Status sugeridos: draft sent viewed approved declined expired cancelled

2.5 quote_items

quote_items

id UUID PK quote_id UUID FK -> quotes.id service_id UUID FK ->
services.id NULL

name TEXT description TEXT NULL quantity NUMERIC unit_price NUMERIC
discount NUMERIC subtotal NUMERIC created_at TIMESTAMP

service_id é uma referência, mas name, description e unit_price devem
ser copiados para preservar o snapshot histórico.

2.6 quote_events

quote_events

id UUID PK quote_id UUID FK -> quotes.id type TEXT metadata JSONB NULL
created_at TIMESTAMP

Eventos: created sent viewed approved declined downloaded

2.7 quote_signatures

quote_signatures

id UUID PK quote_id UUID FK -> quotes.id signer_name TEXT signer_email
TEXT signature_data TEXT NULL signed_at TIMESTAMP ip_address INET NULL

Para o projeto de portfólio, tratar isso como aceite eletrônico. Não
apresentar como assinatura digital qualificada/legalmente certificada.

RELACIONAMENTO GERAL

auth.users │ ▼ profiles ├──────────────┐ ▼ ▼ clients services │ ▼ quotes
├──────────────┬──────────────┐ ▼ ▼ ▼ quote_items quote_events
quote_signatures

SEGURANÇA DO BANCO

-   Ativar RLS em todas as tabelas privadas.
-   Usuário só pode acessar seus próprios clients, services e quotes.
-   quote_items deve ser acessível somente quando o usuário possui o
    quote.
-   A rota pública deve expor somente os dados necessários.
-   Não confiar apenas no frontend para autorização.
-   Validar autorização no servidor/banco.
-   Criar índices para user_id, client_id, quote_id e public_id.

SPRINT 8 — MOTOR DE CÁLCULOS

Criar uma função pura:

calculateQuoteTotals(items, discount, tax)

Retorno:

{ subtotal, discountTotal, taxTotal, total }

Regras:

itemSubtotal = quantity × unitPrice

subtotal = soma dos itemSubtotal

total = subtotal - discountTotal + taxTotal

CUIDADOS COM DINHEIRO

-   PostgreSQL: usar NUMERIC.
-   Evitar cálculos monetários espalhados pela UI.
-   Considerar valores em centavos no frontend ou uma estratégia
    consistente de precisão.
-   Criar testes específicos para os cálculos.

SPRINT 12 — MÁQUINA DE ESTADOS

Fluxo:

DRAFT ↓ enviar SENT ↓ cliente visualiza VIEWED ├──→ APPROVED └──→
DECLINED

Também: SENT → EXPIRED DRAFT → CANCELLED

Regras: - DRAFT: edição permitida. - SENT: edição bloqueada ou criação
de nova versão. - VIEWED: registrar evento. - APPROVED: registrar
aprovação. - DECLINED: registrar recusa. - EXPIRED: impedir aprovação. -
Cliente não pode escolher qualquer status manualmente.

SPRINT 13 — IMUTABILIDADE

Regra crítica:

Depois que o orçamento for enviado, não alterar silenciosamente: -
preço - itens - cliente - total - condições

Para o MVP: - bloquear edição após SENT.

Para uma versão avançada:

Quote #2026-001 Version 1 → R$ 1.500 ↓ Version 2 → R$ 1.700

Cada versão deve preservar seu próprio snapshot.

======================================================================
5. REGRAS DE NEGÓCIO CRÍTICAS
======================================================================

1.  SNAPSHOT O orçamento deve guardar os dados dos itens no momento da
    criação.

2.  DINHEIRO Usar NUMERIC no PostgreSQL e estratégia consistente de
    precisão no frontend.

3.  DESCONTO Definir claramente:

-   percentual ou
-   valor fixo

Validar limites.

4.  IMPOSTOS No MVP, usar regra simples/configurável. Não assumir
    automaticamente regras fiscais brasileiras complexas.

5.  VALIDADE Após a data de validade, impedir aprovação.

6.  IMUTABILIDADE Depois do envio, não alterar silenciosamente o
    documento recebido.

7.  AUTORIZAÇÃO Toda operação privada precisa ser autorizada no
    servidor/banco.

8.  PUBLIC ID Usar UUID/identificador aleatório. Não usar ID sequencial
    como segredo.

9.  EVENTOS Registrar:

-   envio
-   visualização
-   aprovação
-   recusa
-   download quando aplicável

10. CONCORRÊNCIA A aprovação precisa ser validada no servidor para
    impedir ações conflitantes.

11. EXCLUSÃO Considerar soft delete ou impedir exclusão de dados ligados
    a documentos históricos.
